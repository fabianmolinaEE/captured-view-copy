# LoopMate automated loop — vision and prototype UI contract

Updated November 13, 2026. **This is the canonical product vision.** Where any other doc (phase plan, UX checkpoint, demo notes, older AGENTS.md sections) conflicts with it, this file wins. Implementation work after this date follows the UI contract in section 4.

## 1. The loop

LoopMate is an automated improvement loop. Agents do the watching, analysis, experimentation and PR drafting. Humans make three kinds of decision and nothing else.

| #   | Stage                     | Who                              | What happens                                                                                                                                                                                                     |
| --- | ------------------------- | -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Collection                | **Collection agent**             | Continuously picks up new recordings for each product, within the workspace's tuning settings and usage cap.                                                                                                     |
| 2   | Insight analysis          | **Insight agent** (Gemini video) | Looks for product **improvements**: UX, UI, layout and hierarchy, button size and target area, copy and labels, discoverability, effort, feedback, trust and engagement. Bug fixes are one subset, not the goal. |
| 3   | Evidence + suggested test | **Insight agent**                | Each insight carries timestamped evidence highlights (playable in-page) and one suggested A/B test.                                                                                                              |
| 4   | Insight review            | **HUMAN**                        | Watches the highlights, accepts or rejects the insight, and approves, edits or rejects the suggested A/B test.                                                                                                   |
| 5   | Experiment                | **Experiment agent**             | Implements the approved variant, collects screen recordings of the variant, and sends them through the insight agent the same way.                                                                               |
| 6   | Deltas                    | **Insight agent**                | Compares control vs variant recordings and reports user-experience deltas with evidence.                                                                                                                         |
| 7   | PR draft                  | **PR agent**                     | Turns a variant with supporting deltas into a pull request.                                                                                                                                                      |
| 8   | Rollout                   | **HUMAN**                        | Reviews the PR, its deltas and evidence on the Rollouts tab, and merges or declines.                                                                                                                             |

Routing: every insight carries a suggested route, **fix** (clear problem → Fixer) or **experiment** (open question → Experimenter), proposed by the model (`suggested_route`). The human can switch it during review. Approving a fix-routed insight sends it to the Fixer, which produces a simulated fix PR in Rollouts. Approving an experiment-routed test sends it to the Experimenter, which runs the simulated A/B run and then a PR. Both paths end at **Results: PR to your repo** on the Rollouts tab. Primary navigation reads exactly **HQ, Insights, A/B Tests, Rollouts** (desktop and mobile); hero names are internal labels (badges, attribution), never nav items. Rollouts belong to the Experimenter; the Fixer is bugs only and is de-emphasized (not in the demo). Home shows the four scouts in the two-bucket loop: "Two find what to improve. Two change it."

### 1.2 Cohort-level insights: drown out the noise (Fabian, Nov 13, 2026 — planned, not implemented)

The product should not change because **one** user showed us something or struggled once. Insights are meant to be **cohort-level**: the Tracker looks across a sample of sessions, not one video at a time.

- **Two layers.** (1) _Session observations_: today's per-recording Gemini analysis, unchanged. It produces timestamped, evidence-backed observations for one session. (2) _Cohort insights_: a new aggregation step groups similar observations across a **sample window of N sessions** for the same product and screen, and produces the insight a human reviews. Each cohort insight links back to the highlights of every supporting session.
- **Sample size N is tunable** in Settings → Scouts → Tracker. Default **N = 50**. The window is the latest N completed sessions per product. A "minimum support" setting gives the number or share of sessions in the window that must show the pattern (for example, at least 5 of 50, or 10%).
- **Frequency is shown, not implied.** Cards read "Seen in 12 of 50 sessions" with the real denominator. When fewer than N sessions exist, the card says so ("only 5 sessions so far") instead of extrapolating. This builds on `insights.ts`, which already counts distinct sessions once and keeps heuristic priority separate from causal impact.
- **Where the threshold applies.**
  - _Bugs and friction_ (failures, missed taps, retries, confusion): support threshold **required** before an insight surfaces or routes to the Fixer. One user's failure is a session observation, not a fix.
  - _Improvement opportunities_ (design, UX, engagement ideas such as a reorder button): may surface below threshold, labeled **"Hypothesis · seen in k of N"**, because the Experimenter's A/B test is the population-level validation. They cannot route to Fixer as a direct fix without meeting the threshold.
  - _Competitor patterns_ (Explorer): a pattern in competitor footage is inspiration, not frequency evidence. Labeled "Competitor pattern", never given a user frequency.
- **Experiments are measured at the population level too.** Variant deltas compare the cohorts of control and variant sessions (the 20% traffic split), never a single recording.
- **Current prototype gap (honest label).** Today every Uber Eats and Bag Checkout insight comes from a single session (n = 1). The Uber Eats demo uses public tutorial videos, which are not representative customers. Until aggregation exists, the UI should say "Single-session observation (n = 1)" on insight cards. Aggregation is a Phase 3 task (see PROTOTYPE-PHASE-PLAN.md 3.6–3.8).

Humans touch exactly three things: **insight review with highlights**, **A/B test approve / edit / reject**, and **PR merge**. Manual recording, the Analyze button, Evaluation and ground-truth labelling are diagnostic research tools, not part of the operating loop. They stay available under Research tools.

## 3. Prototype status per stage

The UI shows the **whole loop**. Every stage has an honest status label.

**Decision (Fabian, Nov 13, 2026):** stages that are not connected yet are shown with **labeled simulated sample data** rather than empty states, so the Sunday demo shows the experiment agent appearing to go out and test. Real by Sunday: insight generation (Gemini) with evidence highlights and suggested tests. Simulated: experiment runs, variant recordings, deltas, PRs. Rules for simulation:

- Every simulated record carries `simulated: true` and shows a visible "Simulated demo" badge wherever it is displayed, including on cards, detail views, Rollouts rows and Home. The label is never hidden behind a tooltip only.
- Simulated records are stored separately from research sessions (their own local store/key), are excluded from Insights priorities, Evaluation metrics and any real counters, and can be cleared from Settings with "Reset simulated demo data".
- Approving a test starts a **client-side simulated experiment run**. It advances through visible stages (Building variant → Collecting variant recordings → Analyzing → Comparing deltas → Drafting PR) over a short timer of tens of seconds. It ends with labeled sample deltas and a simulated PR in Rollouts. Nothing is deployed, no repository is touched, and no network call is made for the simulation.
- Sample deltas are deterministic placeholders derived from the test, clearly marked "illustrative, not measured". They are never presented as statistical results.

## 4. UI contract (implemented November 13; browser QA pending)

### 4.1 Suggested test on each finding

The model output gains an optional `suggested_test`. It goes into the Zod `proposalSchema` and the provider JSON schema, but is **not** required in the provider schema. The model is asked to return it whenever it proposes a concrete change.

```ts
interface SuggestedTest {
  // model original, never mutated
  hypothesis: string; // "If we …, then … because …"
  change: string; // variant description vs current control
  primary_metric: string; // e.g. "checkout completion", "time to add item"
  guardrail_metric?: string; // e.g. "order errors"
  target_screen?: string;
}
interface TestDecision {
  // human fields, stored separately
  decision: "pending" | "approved" | "rejected";
  edited: boolean;
  edited_test?: SuggestedTest; // human copy; present only when edited
  decided_at?: string;
}
// Finding: suggested_test?: SuggestedTest; test_decision?: TestDecision
```

- The model's `suggested_test` and `raw_output` are preserved verbatim. Edits write only to `test_decision.edited_test`, and the UI labels which version is shown ("Edited by reviewer" vs "Agent suggestion").
- **Decision rule:** a test can be approved only once its insight is accepted. The detail page offers a single **"Accept insight & approve test"** action, which sets `review_status: "accepted"` and `decision: "approved"` in one queued write. Plain "Approve test" stays disabled while the insight is pending or rejected. Rejecting or reopening the insight resets an approved test to `pending`. Editing a test after approval sets it back to `pending` (the same rule `actions.ts` uses for drafts today). Empty hypothesis, change or primary metric blocks approval.
- Approval starts only the labeled client-side **simulated** experiment run (section 3). It performs no real experiment, repository write or deployment, and the UI says so.
- Validation: the metric strings are free text, and the model must not supply numbers, uplift estimates or sample sizes. Any `suggested_test` field that fails validation fails the run, matching the current strictness.
- The prompt adds one instruction: propose one falsifiable test for the improvement, measurable on screen recordings, with no predicted effect size.

### 4.2 Legacy next-step drafts

Existing `next_step` drafts stay readable on finding detail as "Earlier research draft". They are never fed to the model. New UI does not create them.

### 4.5 Uber Eats in-page playback

- Use the official YouTube IFrame Player API (`https://www.youtube.com/iframe_api`) with an embed that sets `enablejsapi=1`, `origin=window.location.origin` and `playsinline=1`, plus `start`/`end` bounding the saved clip. Highlights call `seekTo(seconds, true)`. `PublicVideoPlayer.tsx` already does this. Keep it, and reuse it for candidate previews in Recordings.
- Viewers never need to leave for YouTube. A "Watch on YouTube" link appears **only** when the player reports a blocked, private or removed embed (`youtubePlaybackError`).
- Attribution (creator, published label) stays visible next to the player. Video bytes are never downloaded or copied.

## 5. Invariants kept

- `blindPayload` enumerates model inputs explicitly. Public video sends only URL plus clip, with no events. Planted scenarios, ground truth, notes, drafts, test decisions and prior answers never reach the model. Focus areas are a fixed enum.
- Invalid timestamps, unknown event IDs and malformed output fail the run. Nothing is silently repaired.
- Model original output stays separate from human edits and decisions.
- No unlabeled or fabricated-as-real metrics, sessions, experiments, deltas, PRs or usage. Simulated demo records are always badged and excluded from research metrics. Heuristic priority is not causal impact.
- Secrets stay in `*.server.ts`. The Gemini call remains server-side.
- Lovable rules apply: no migrations, no edits to generated files, no history rewrites. The IndexedDB name is unchanged.
- Theme: continuous purple/navy `data-theme="loop"`. `.phone` keeps its light storefront palette and capture geometry.
